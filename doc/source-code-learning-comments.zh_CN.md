# Linux 内核源码学习注释标准

## 1. 定位与目标

本文件是仓库内向 `.c`、`.h` 等内核源码添加中文学习注释时的唯一执行与验收标准。

- `linux-kernel-source-learning-methodology.md`：说明主题文档、源码注释、问题和实验如何组成学习闭环；
- `linux-kernel-internals-writing-guide.md`：约束独立主题文章；
- 本文件：约束源码里的中文学习注释。

默认读者具有工程经验，但不熟悉 Linux 内核、当前子系统或复杂 C 惯用法。注释需要帮助读者获得
内核开发者走读代码时主动恢复的上下文，而不是把 C 代码逐句翻译成中文。

读完一个完整注释的文件后，读者应能回答：

1. 文件解决什么问题，处于哪条调用链；
2. 核心对象如何创建、发布、引用、摘除和销毁；
3. 函数的输入、输出、副作用和失败语义；
4. 锁、RCU、引用计数和内存屏障分别保证什么；
5. fast path、slow path、回滚和释放路径如何衔接；
6. 为什么采用当前方案，它获得什么、付出什么。

## 2. 不可违反的规则

### 2.1 只增加学习注释

- 不修改任何可执行代码、声明、宏续行、条件编译结构或原有格式；
- 不删除、改写、移动、合并或拆分任何已有注释；
- 英文注释必须原样保留，并在紧邻位置补充中文解释；
- 已有注释不完整时，在其下方追加独立的“补充说明”；
- 已有注释错误或只适用于特定版本/架构时，在其下方追加有源码依据的“修正说明”；
- 预处理器反斜杠续行之间不得插入独立注释行。

许可证、版权名单和纯 ASCII 示意图不要求翻译。短小行尾英文注释可以由同一局部代码块的中文
说明覆盖，但读者必须能明确建立对应关系。

### 2.2 结论必须有证据

- 调用关系以当前源码为准，不凭函数名猜测；
- 锁的保护范围、RCU 配对、所有权和返回约定必须从实现或接口契约核对；
- 区分当前实现、稳定接口、推论和设计动机；
- 不把引用计数、锁、RCU、编译器屏障、硬件内存屏障混为一谈；
- 不把清页表、TLB flush、cache flush 和释放物理页描述成同一操作；
- 性能结论必须说明成立条件，不使用“必然更快”“完全无锁”等绝对表述。

查询其他文件是为了证明目标文件中的结论。除非用户明确要求，不顺带修改查询过程中阅读的文件。

### 2.3 注释行为，不教学普通语法

不解释普通赋值、循环、条件判断、`return 0`、括号和分号。需要解释的是：

- 指针/整数地址转换、指针算术单位和对齐；
- 位图、位域、错误指针和侵入式容器；
- 宏、内联、`__init`、`__read_mostly` 等在当前路径中的实际影响；
- GFP、RCU、per-CPU、NUMA、页表、TLB、引用计数等内核机制；
- 一行代码隐藏的所有权转移、发布、回收、内存序或硬件副作用。

禁止使用“中文说明：”“中文学习注释：”“逐行学习：”“中文解释：”“背景知识：”等元标签，
直接写行为、约束和原因，也不要为了提高注释行数复述代码。该规则只约束后续新增注释；除非
用户明确要求，不为统一风格而清理源码中已经存在的标签。

## 3. 四层覆盖模型

完整注释必须同时具有以下四层。

### 3.1 文件地图

文件头新增学习导读，至少说明：

- 中文学习注释的生成模型及版本，便于交叉比较；
- 文件职责和不负责的边界；
- 主要入口、主调用链和后续去向；
- 核心对象及其生命周期；
- 主要并发模型；
- 当前方案的收益、代价和适用条件。

模型标识放在原版权块之前，不写入上游作者列表，不改动版权内容。

### 3.2 对象与函数契约

每个命名实体都必须能让读者理解它为什么存在：

- **函数**：职责、调用位置、输入输出、副作用、上下文、锁、所有权和失败结果；
- **结构体**：代表的对象/快照、创建者、持有者、发布与销毁方式、同步规则；
- **字段**：按不变量分组说明业务意义、单位、有效阶段及与其他字段的关系；
- **全局/静态变量**：用途、读写者、生命周期、保护方式和特殊初值；
- **参数**：业务含义、单位、范围、可空性、输入/输出属性和所有权；
- **局部变量**：通过变量地图或相邻阶段说明其角色、单位和有效阶段。

简单 getter、stub、薄包装和纯算术临时量可以成组解释，但不能完全跳过；组注释必须明确每个成员
固定了什么参数、配置或策略。解释重点是协议中的角色，不是 C 类型的中文名称。

### 3.3 函数阶段块

长函数按状态变化划分为准备、校验、查找、获取资源、发布、等待、回滚和释放等阶段。每个阶段说明：

- 进入时已有的对象和状态；
- 本阶段解决的局部问题；
- 关键调用和状态变化；
- 完成后建立的不变量；
- 失败时转入哪个清理阶段。

通常在控制流、所有权或状态阶段发生切换时增加新说明。不能用一个很长的函数头注释替代函数体内
的走读线索，也不使用固定的“每几行一条注释”指标。

### 3.4 隐藏语义语句

以下语句必须就地解释，除非其语义已被紧邻阶段块完整覆盖：

- 锁、RCU、原子操作、`READ_ONCE`/`WRITE_ONCE` 和内存屏障；
- 引用获取/释放、所有权转移和对象发布/摘除；
- GFP 调整、错误指针、溢出/边界检查和单位换算；
- 页表更新、TLB/cache 操作、设备寄存器和跨 CPU 操作；
- 多资源 `goto` 回滚、不可回滚点和特殊配置/架构分支。

注释密度由隐藏状态变化决定，不由语法复杂度或物理行数决定。

## 4. 函数与调用注释标准

### 4.1 函数入口

公共函数、主路径函数、资源生命周期函数、并发函数、错误回滚函数和具有隐藏副作用的 helper，
必须在声明正上方拥有专属中文说明。已有英文 kernel-doc 时，中文说明放在英文块之后。

至少覆盖适用项：

```text
一句话职责和宏观调用位置
主要调用者及返回后的去向
全部参数的业务含义、单位、范围、可空性和 ownership
入口对象状态、锁状态、执行上下文以及能否睡眠
主要执行阶段和关键方案选择
返回值、输出参数和其他可观察副作用
成功后建立的不变量
失败值的精确含义及剩余资源由谁清理
```

无参数、无返回值或无副作用时可以简写，但不能让读者自行猜测。

### 4.2 关键 helper 调用

顺序阅读时，读者不应仅凭函数名猜测外部 helper。对会改变资源、所有权、并发或硬件状态的调用，
局部说明至少回答：

1. 为什么在当前阶段调用；
2. 输入对象现在处于什么状态；
3. 成功后改变什么，返回的是值、借用指针、持有引用还是错误指针；
4. 失败后当前函数还拥有什么，是否需要回滚；
5. 是否可能睡眠、触发 reclaim、调度工作、跨 CPU 执行或进入架构代码。

第一次出现核心 helper 时可以建立完整模型；后续只说明本次调用的特殊输入和影响。禁止只写
“调用 `free_pages()` 释放页面”这类函数名翻译。

## 5. 必须讲透的内核语义

### 5.1 生命周期与所有权

每个核心对象都应形成闭环：

```text
在哪里分配
何时初始化完成
何时进入全局可发现状态
谁持有引用、锁或所有权
何时从索引摘除
何时解除硬件可见状态
何时最终释放
```

明确区分裸指针、借用指针、持有引用和所有权转移。引用保证对象存储期，不保证字段不变化；锁保护
约定内的状态，不自动延长对象寿命。

### 5.2 并发与内存序

不能只写“加锁保证线程安全”。应说明：

- 被保护的对象或字段；
- 竞争双方分别是谁；
- 读者遵循什么协议；
- 与哪个写入、屏障、解锁或宽限期配对；
- 删除或换序后会产生何种具体问题，如重复领取、丢失更新、UAF、旧映射或半初始化对象。

### 5.3 错误回滚

对多阶段资源获取和 `goto` 清理链，说明每个标签到达时：

- 哪些资源已经取得；
- 哪些状态尚未发布；
- 为什么按当前逆序释放；
- 返回后是否仍有资源或引用转移给调用者。

### 5.4 方案权衡

关键设计应说明为什么不用更简单方案，并同时写出：

```text
当前方案解决的问题
获得的性能、扩展性或安全收益
增加的空间、复杂度、延迟或维护成本
退化、回收或 fallback 条件
```

## 6. 工作流程

### 6.1 新会话启动

1. 完整阅读本文件；
2. 确认目标、分支和工作区状态，保护用户已有修改；
3. 判断是全文件初注、续写、缺口补全还是质量验收；
4. 提取函数、结构体、全局/静态变量、条件编译和英文注释块清单；
5. 建立文件职责、主调用链、对象生命周期和并发地图；
6. 检查已有中文注释，正确内容增量保留，不因换会话而重写。

### 6.2 顺序实施

建立地图后，从文件第一行按物理顺序走到最后一行。搜索只用于核对定义、调用者、配置和架构实现，
不能代替对当前文件上下文的连续阅读。

大文件采用：

```text
地图一次建立
→ 按较大连续区域批量注释
→ 每个区域做局部复核
→ 接近完成时统一执行全文件审计
```

速度来自减少重复扫描、批量推进和复用已建立模型，不能靠跳过函数、变量、失败路径或并发论证。
进度报告说明已覆盖范围和遗留路径，不以新增行数表示完成度。

跨文件追踪在被调函数不再改变当前问题的状态、所有权、并发或硬件边界时停止，避免无限扩散。

## 7. 验收清单

### 7.1 内容审计

- **函数清单**：每个函数标记为独立详细说明、函数组覆盖或简单但已说明，不得缺失；
- **实体清单**：结构体、关键字段、全局/静态变量、参数和局部变量均能理解其业务角色；
- **英文注释**：逐块确认原文未变，并有紧邻中文解释或明确的局部覆盖；
- **路径覆盖**：成功、slow path、失败回滚、释放、并发读取和配置/架构 fallback；
- **生命周期**：核心对象从创建到最终释放形成闭环；
- **关键语句**：锁、RCU、原子、屏障、引用、页表、TLB/cache、GFP、错误指针和单位换算；
- **helper 调用**：关键调用的输入状态、输出、副作用、失败语义和调用时机清楚；
- **噪声检查**：无模板前缀、普通语法翻译、无关百科和重复定义。

至少抽查三个复杂函数，只读注释复述其入口条件、执行阶段、状态变化、并发对手、失败路径和返回保证。
需要依靠猜测才能回答的项目视为缺口。

### 7.2 修改安全验证

至少执行：

```bash
git diff --check -- <目标文件>
git diff --stat -- <目标文件>
git diff -- <目标文件>
```

人工确认没有代码、声明、宏、条件编译和原有注释变化，新注释没有意外注释掉代码。有可用 `.config`
和工具链时编译目标对象；无法编译时明确报告“未完成编译验证”。

`git diff --check` 只检查空白格式，不能证明内容达到标准。

## 8. 完成与交付状态

最终只能使用以下三种状态：

- **全文件完成**：四层覆盖齐全，所有清单无缺口，生命周期闭环，验证通过；
- **主路径检查点完成**：约定主路径达到标准，但仍有函数、配置分支或边缘路径未覆盖；
- **尚未达到标准**：存在阻碍顺序阅读或可能导致错误理解的关键缺口。

不得用“基本完成”“注释很多”“格式检查通过”代替明确状态。用户要求阶段提交时可以提交主路径
检查点，但提交信息和交付说明必须明确它不是最终状态。

若用户只说“添加详尽注释”，默认目标是全文件完成；不能自行降级为主路径检查点。

## 9. 精简模板

### 9.1 文件头

```c
/*
 * 文件/子系统学习导读
 *
 * 中文学习注释模型：厂商、产品和版本。
 * 职责边界：解决什么问题，不负责什么。
 * 主调用链：入口 -> 核心阶段 -> 发布/返回；失败 -> 回滚；释放 -> 最终回收。
 * 核心对象：对象关系、生命周期和 ownership。
 * 并发模型：锁、RCU、per-CPU 或硬件同步分别保护什么。
 * 方案权衡：收益、代价和 fallback。
 */
```

### 9.2 函数入口

```c
/*
 * function_name - 用业务语义说明职责。
 *
 * 调用关系：谁调用，结果交给谁。
 * 入参与前置条件：单位、范围、ownership、锁和执行上下文。
 * 核心过程：主要阶段和关键设计理由。
 * 返回与副作用：输出、状态变化和成功保证。
 * 失败结果：错误含义、剩余资源和回滚责任。
 */
```

模板用于提醒信息维度，不能机械填栏目或复制与当前函数无关的句子。

## 10. 新会话任务模板

```text
请完整阅读 ./doc/source-code-learning-comments.zh_CN.md，并以它作为本次源码注释任务的唯一执行与
验收标准。目标文件：<path>。

只增加中文学习注释，不修改代码、格式和任何已有注释。先建立文件地图，再按源码物理顺序完整
走读。解释函数、结构体、字段、变量和关键 helper 在当前协议中的角色，重点讲清状态变化、所有权、
生命周期、锁/RCU/内存序、错误回滚、硬件副作用和方案权衡，不翻译普通 C 语法。

完成后执行内容清单和修改安全验证；最终只能报告“全文件完成”“主路径检查点完成”或“尚未达到
标准”，并列出验证证据和遗留项。
```
