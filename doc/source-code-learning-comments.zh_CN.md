# Linux 内核源码学习注释标准

## 1. 目的

本标准用于给 Linux 内核源码添加面向学习者的中文注释。注释的目标不是翻译 C
代码，也不是替代内核原有英文注释，而是补足阅读源码时无法仅从语句本身得到的
上下文：代码为何存在、依赖哪些内核机制、维护什么不变量、为何选择当前方案、
失败时如何回滚，以及该方案在性能、复杂度和安全性上的取舍。

完成注释后，读者应当能够：

1. 在进入实现细节前说清楚文件负责什么、不负责什么；
2. 沿主要调用链从公共入口跟到核心实现和释放路径；
3. 理解关键数据结构的所有权、生命周期和并发保护方式；
4. 理解内核特有 API、C 用法和硬件机制在当前代码中的实际意义；
5. 判断关键条件分支、内存屏障、锁和错误回滚为何不能随意删除或换序；
6. 说出当前方案相对于更简单方案的主要收益与代价。

## 2. 目标读者

默认读者是具有多年工程经验的程序员，但不熟悉 C、Linux 内核或当前子系统。

因此：

- 不解释普通的赋值、循环、布尔判断和函数调用概念；
- 需要解释指针运算、位操作、宏、container_of、侵入式链表、错误指针等 C/内核
  特有表达；
- 需要解释 GFP、RCU、per-CPU、NUMA、页表、TLB、内存屏障、引用计数等内核概念；
- 第一次出现术语时建立完整心智模型，后续只说明其在当前路径中的特殊作用；
- 假设读者能理解复杂系统设计，不回避不变量、并发时序和性能模型。

“不熟悉 C”不代表需要语法教程。注释应把连续几行代码归纳为功能单元，说明当前
阶段、输入状态、完成的操作、输出状态和注意事项，让读者通过注释获得资深 C/内核
工程师走读代码时形成的结论。只有单行代码存在隐藏副作用、单位变化或状态发布时，
才需要行内说明；不单独讲解 `&`、`*`、循环、三元表达式等普通 C 语法。

## 3. 总原则

### 3.1 解释代码之外的信息

优先回答以下问题：

- 为什么需要这段代码？
- 它在调用链的什么位置？谁建立前置条件，谁消费结果？
- 这里维护的核心不变量是什么？
- 为什么采用该数据结构、同步原语或执行顺序？
- 更直接的实现为什么不可取？
- 当前方案获得了什么，又付出了什么？
- 失败发生后，哪些资源已经取得，必须以什么顺序归还？
- 如果删除、换序或放宽某个检查，会产生什么具体故障？

下面这种注释通常没有价值：

```c
/* 将 count 加一。 */
count++;

/* 如果 page 为空则返回。 */
if (!page)
	return NULL;
```

除非 `count` 的并发语义或 `NULL` 所代表的状态并不直观，否则代码本身已经完整
表达了这些信息。

### 3.2 注释应贴近证据

文件级背景放在文件头；函数契约放在函数入口；分支存在的原因放在对应条件前；
执行顺序的约束放在第一步操作前；字段不变量放在结构体或字段旁。不要把所有知识
堆进一个远离实现的大段总览，迫使读者来回搜索。

### 3.3 先建立模型，再解释细节

注释采用从宏观到局部的层次：

1. 文件和子系统模型；
2. 主调用链与资源生命周期；
3. 数据结构和并发模型；
4. 函数职责与契约；
5. 关键代码块和关键语句。

只有第五层而没有前四层，会变成碎片化翻译；只有前四层而没有第五层，则无法陪伴
读者逐段阅读源码。

### 3.4 保留上游内容和代码语义

- 源码中已有的英文注释必须逐字保留，不得删除、改写、缩写、移动或用中文替换；
- 中文说明只能追加在原英文注释的紧邻位置；即使英文内容存在拼写、语法或表述问题，
  也不得顺手修正，除非任务明确包含修改上游代码；
- 不修改任何可执行逻辑、声明、宏续行或条件编译结构；
- 不为插入注释而改变代码格式；
- 预处理器反斜杠续行中不得插入会终止宏定义的独立注释行；
- 注释中的结论必须能由当前版本源码或可靠的内核机制支持。

### 3.5 英文原注释必须有中文解释

保留英文原文不等于完成中文学习注释。每个完整英文块注释都必须在紧邻位置提供
中文解释，至少覆盖原文表达的契约、背景和限制；复杂注释还应补充原文默认读者
已经掌握的内核背景。中文说明不能只逐句直译，也不能遗漏英文中的警告、调用上下文、
返回值或所有权约束。

短小行尾注释可以合并到所属代码块的中文说明中，但必须能够从局部位置明确找到
对应解释。许可证、版权人名单和纯 ASCII 区间示意图不要求翻译。

## 4. 覆盖标准

“覆盖完整”不等于每一物理行前都有注释。覆盖单位是语义单元，而不是行号。

### 4.1 文件级覆盖

每个文件必须包含：

- 中文学习注释的生成模型，使用可交叉比较的明确名称；
- 文件在内核中的职责边界；
- 面向外部的主要 API；
- 至少一条主要调用链；
- 核心数据结构之间的关系；
- 资源从分配、发布到回收的生命周期；
- 主要并发机制；
- 当前设计的主要优点、缺点和适用场景。

### 4.2 区域级覆盖

每个重要实现区域必须说明：

- 该区域解决的子问题；
- 输入和输出的数据表示；
- 与前后区域的边界；
- 该区域共同维护的不变量；
- 主要 fast path、slow path 和 fallback；
- 性能与复杂度取舍。

### 4.3 函数级覆盖

以下函数必须逐个说明，不能只依赖区域总览：

- 公共或导出函数；
- 主调用链上的函数；
- 分配、发布、查找、解除映射和释放函数；
- 持锁、切换上下文或使用 RCU 的函数；
- 错误回滚和延迟工作函数；
- 名称无法直接表达副作用的 helper；
- 依赖特殊调用约定的函数。

每个此类函数的注释至少覆盖适用项：

- 一句话职责；
- 调用者和被调用者；
- **逐项说明全部入参**：每个参数代表什么、单位是什么、允许范围、对齐要求、
  是否可为 `NULL`、输入/输出属性，以及调用前后所有权是否变化；
- **明确说明出参和返回值**：包括返回对象或数值的含义，以及 `NULL`、错误码、
  错误指针、布尔值和部分成功分别代表什么；
- 没有显式返回值的函数也要说明其可观察输出，例如修改的对象字段、全局索引、
  页表、锁状态、引用计数、调度工作或释放的资源；
- 调用上下文：是否可睡眠，能否在中断/NMI 中调用；
- 进入和返回时的锁状态；
- 成功后建立的不变量；
- 失败后的资源状态；
- 关键方案取舍。

简单、无状态、名称完全自解释的 getter 或薄包装可以按函数组解释，但必须明确列出
该组中各包装函数固定了哪些策略，不能完全跳过。

区域级注释、相邻函数注释和英文 kernel-doc 均不能替代函数自己的中文覆盖。
验收时应从函数声明开始，只检查该函数专属的中文注释，不得以“前后若干行内出现
中文”作为已覆盖依据。

### 4.4 代码块级覆盖

以下代码块必须在局部解释：

- 不直观的提前返回；
- fast path 与 fallback 的分界；
- 重试、回收和降级路径；
- 多阶段资源获取及 `goto` 回滚链；
- 两个以上锁或多个索引的更新顺序；
- RCU 发布、摘除和延迟释放；
- 内存屏障及与之配对的读写操作；
- TLB/cache flush 的范围与执行时机；
- 溢出、对齐和边界检查；
- 看起来可以合并但实际必须分开的状态；
- 为兼容架构、配置或启动阶段而保留的替代路径。

### 4.5 关键语句级覆盖

仅在语句包含隐藏语义时添加行内或紧邻注释，例如：

- `xchg`/`cmpxchg` 同时完成所有权转移和并发仲裁；
- `READ_ONCE`/`WRITE_ONCE` 防止编译器合并或撕裂访问；
- `smp_rmb`/`smp_wmb` 与另一个发布点配对；
- `container_of` 从嵌入成员恢复宿主对象；
- `kfree_rcu` 表示对象已不可发现，但存储要等宽限期后释放；
- `ERR_PTR` 在指针中编码错误码；
- `__GFP_*` 改变 reclaim、IO、文件系统重入或失败语义；
- 页表 helper 可能表示 huge leaf，而非下一级页表指针；
- 位域同时编码类型、状态或 node id。

函数入口已有长注释，不代表函数内部不再需要注释。凡是语句的正确性依赖隐藏的
单位、所有权转移、锁状态、内存顺序、硬件缓存状态或错误标签资源状态，都必须在
该语句或紧邻代码块处解释。

### 4.6 函数调用级覆盖

顺序走读时，读者不应被迫仅凭函数名猜测调用含义。对下列调用，应在调用前或所在
代码块中用一两句话说明其作用及其对当前路径的影响：

- 当前文件之外定义、且名称不足以推断真实行为的内核 helper；
- 会分配、释放、获取引用、改变所有权、发布对象或修改全局索引的调用；
- 会睡眠、触发 reclaim、调度 work、执行跨 CPU 操作或进入架构代码的调用；
- 会修改页表、TLB、CPU cache、direct map、KASAN/KMSAN/kmemleak 状态的调用；
- 返回值存在特殊约定，例如错误指针、部分完成数量、带锁返回或借用指针的调用；
- 调用失败后需要当前函数回滚已取得资源的调用。

说明至少回答当前语境中最重要的三件事：它做什么、成功或失败后改变了什么、为什么
当前阶段要调用它。首次遇到核心 helper 时可以解释其通用机制；后续调用只说明在
当前路径中的特殊作用，不重复百科式定义。

名称和副作用完全自解释的局部纯函数、简单 getter、普通算术 helper 不要求逐次说明。
禁止仅把函数名拆词翻译，例如“调用 `free_pages()` 释放页面”；应补充页面所有权、
引用/记账变化或为什么此刻已经满足安全释放条件。

## 5. 注释内容模型

### 5.1 文件头模板

```c
/*
 * 文件/子系统学习导读
 *
 * 中文学习注释模型：厂商及产品名称（具体模型名称或版本）。此标识仅说明新增
 * 中文注释的来源，不属于上游源码署名，便于与其他模型生成结果交叉比较。
 *
 * 文件职责：该子系统要解决什么问题，为什么普通机制不够。
 *
 * 主调用链：
 *   API -> 核心入口 -> 子资源分配 -> 发布
 *                         -> 失败回滚
 *   释放 API -> 摘除 -> 解除硬件状态 -> 延迟回收
 *
 * 核心对象：对象 A 表示什么，对象 B 表示什么，谁拥有谁。
 *
 * 并发模型：哪些锁保护哪些状态，哪些读者使用 RCU/per-CPU。
 *
 * 方案权衡：为什么不用更简单的方案，当前方案的收益和代价。
 */
```

模型标识必须位于文件头部新增的学习导读中，并出现在原始版权或作者注释之前。
不得修改上游版权块，也不得把模型名称写入上游作者列表。模型名称应尽量精确到实际
生成注释的模型或版本；无法取得版本时，至少写明厂商和产品名称，不得只写“AI”。

### 5.2 函数注释模板

```c
/*
 * function_name - 用业务语义描述职责，而不是复述函数名
 *
 * 调用关系：由谁调用，成功后结果交给谁。
 * 入参：逐项说明含义、单位、合法范围、可空性、对齐及所有权。
 * 前置条件：锁、上下文和对象状态。
 * 核心机制：解释实现选择及不能采用简单方案的原因。
 * 出参/返回：返回值、输出参数、副作用以及成功后建立的不变量。
 * 失败结果：NULL/错误码/错误指针的精确含义，以及已取得资源由谁清理。
 * 权衡：性能、空间、复杂度或安全性。
 */
```

不是每个函数都要机械填满所有栏目，但入参、出参/返回和可观察副作用不得省略；
无参数、无返回值或无副作用时应明确说明，而不是让读者自行猜测。

函数级注释必须放在函数声明（函数名）正上方，不得放进函数体的开头。这样阅读者
在进入实现前就能看到职责和契约，也能通过搜索函数声明快速浏览。函数体内只保留
针对具体分支、状态转换和关键语句的局部注释。若已有英文 kernel-doc，则中文函数
说明放在英文块之后、函数声明之前，二者都保留。

### 5.3 并发注释模板

```c
/*
 * 此处先从全局索引摘除对象，使新读者无法获得它；已有 RCU 读者仍可能持有
 * 指针，因此只能在宽限期后释放存储。先 kfree 再摘除会产生 UAF；仅摘除而
 * 不延迟释放也不够。
 */
```

### 5.4 错误回滚模板

```c
/*
 * 到达此标签时 A、B 已创建，C 尚未发布。按 C <- B <- A 的逆序回滚，可避免
 * B 的析构仍需访问 A 时 A 已先被释放。该路径返回后不转移任何资源所有权。
 */
```

### 5.5 方案权衡模板

```c
/*
 * 这里缓存空闲对象以避开全局锁和重新分配。收益是热路径延迟更低；代价是对象
 * 短期不能参与全局合并，增加内存占用和碎片。压力路径会主动衰减缓存，因此该
 * 优化不改变最终可回收性。
 */
```

## 6. C 与内核知识的解释边界

### 6.1 应当解释

- C 指针和整数地址之间的转换为何安全或受哪些范围限制；
- 指针算术的单位，以及为何要先转成字节地址；
- `static`、`inline`、`__init`、`__read_mostly` 等属性在当前对象上的实际影响；
- 宏为何不能用普通函数替代；
- 侵入式容器中对象和节点的生命周期关系；
- 内核错误处理为何常用 `goto`，以及具体标签拥有哪些资源；
- 配置关闭时 stub/常量回退如何保持调用者语义；
- 架构折叠页表层时统一接口如何工作。

### 6.2 不应当解释

- `i++` 表示递增；
- `if` 表示条件判断；
- `return 0` 表示返回零；
- 每个局部变量都重复“用于保存某值”；
- 每个 `#include` 都使用相同的“引入依赖”描述；
- 每个函数调用都只把英文函数名翻译成中文；
- 单纯为了提高注释行数而解释括号、分号和代码换行。

### 6.3 同一知识只完整解释一次

第一次出现 RCU、GFP 或 TLB shootdown 时可以详细建立模型。后续位置应说明它在
当前路径中的差异，例如“这里不能立即 `kfree`，因为前面的 xarray 查询处于 RCU
读侧”，而不是重复 RCU 的通用定义。

## 7. 准确性要求

- 区分事实、推论和经验性解释；无法从源码确认的动机不要写成确定事实；
- 不把 CPU cache、编译器屏障和硬件内存屏障混为一谈；
- 不把“当前实现碰巧如此”描述为稳定 API；
- 不声称锁提供了它实际没有提供的保护；
- 不把 per-CPU 数据误解为只能由对应 CPU 访问；
- 不把 NUMA node、CPU、vmap node 等不同概念混用；
- 不把清页表、TLB flush、cache flush 和释放物理页视为同一个操作；
- 性能结论应说明条件，避免“必然更快”“完全无锁”等绝对表达；
- 示例必须帮助建立正确模型，不为生动而牺牲准确性。

## 8. 密度与覆盖验收

不使用固定的“注释与代码行数比例”作为唯一指标，但应完成以下审计：

### 8.1 函数清单审计

列出文件全部函数，并标记：

- `D`：已有独立详细注释；
- `G`：由紧邻的函数组注释覆盖；
- `S`：简单自解释，无需新增注释；
- `M`：缺失，必须补充。

最终不得存在 `M`。`S` 必须能用一句话说明为何无需注释，不能作为批量跳过复杂
helper 的借口。

函数审计、英文块审计和关键语句审计是三张独立清单。某函数标记为 `D`，不代表
其中的英文块或隐藏语义语句自动通过另外两项审计。

### 8.2 英文注释块审计

提取文件中所有完整英文块注释，逐项标记：

- `T`：紧邻位置已有完整中文解释；
- `G`：短注释已由同一局部代码块的中文说明明确覆盖；
- `E`：许可证、版权或无需翻译的纯示意图；
- `M`：缺少中文解释。

最终不得存在 `M`。不能因为文件其他位置介绍过同一通用概念，就省略该英文注释
在当前代码位置表达的特殊约束。

审计前后还必须比较原始版本，确认英文注释的文本、位置和数量均未变化；发现删除、
替换、移动或顺手修订的英文注释，应先恢复原文，再追加中文解释。

### 8.3 路径审计

至少从源码中完整走读并注释：

- 一条成功 fast path；
- 一条资源不足 slow path；
- 一条中途失败回滚路径；
- 一条释放路径；
- 一条并发读取或诊断路径；
- 一条配置或架构 fallback 路径。

### 8.4 对象生命周期审计

每个核心对象都能在注释中回答：

- 在哪里分配；
- 何时进入全局可发现状态；
- 谁拥有引用或锁；
- 在哪里从索引摘除；
- 何时解除硬件可见状态；
- 在哪里最终释放。

### 8.5 关键语句审计

逐函数检查包含下列模式的语句：锁和解锁、RCU、原子交换、一次性读写、内存屏障、
页表修改、TLB/cache flush、GFP 调整、错误指针、溢出检查、地址/页数单位换算和
`goto` 标签。每一处必须由局部中文说明覆盖，或能明确证明语义完全自解释。

### 8.6 函数调用审计

逐函数检查外部 helper 和具有资源、并发、硬件或错误语义的调用。读到调用位置时，
注释应足以判断：被调用者的核心作用、当前路径依赖的返回约定、成功后的状态变化、
失败时是否需要回滚。无法仅凭局部注释回答这些问题的调用标记为 `M` 并补充说明。

### 8.7 噪声审计

搜索并删除：

- 重复前缀，例如“逐行学习：”；
- 声明注释语言或类别的元标签，例如“中文补充：”“中文解释：”“背景知识：”；
- 可以无损替换到任意文件的模板句；
- 只复述相邻代码的注释；
- 与当前函数无关的百科式长段落；
- 重复解释且未增加局部信息的术语定义。

## 9. 工作流程

### 第一阶段：建立地图

1. 阅读文件头、结构体、区域标题和公共 API；
2. 提取完整函数清单；
3. 画出主要调用链和对象生命周期；
4. 标记锁、RCU、per-CPU、workqueue、页表和错误标签；
5. 记录尚不确定、需要从头文件或调用者确认的问题。

### 第二阶段：从文件第一行顺序走读

完成初始地图后，必须严格按照源码物理顺序从第一行走到最后一行，不得先按函数名、
API 模式或关键字搜索批量填充注释。搜索工具只用于确认调用者、定义和架构实现，
不能替代当前代码上下文的顺序阅读。

每到一个新的区域、结构体或函数，按以下次序判断：

1. 当前代码在整个文件调用链中走到了哪个阶段；
2. 这一段依赖什么 C、内核子系统或硬件背景；
3. 它维护什么状态和不变量；
4. 为什么选择当前设计，替代方案有什么问题；
5. 接下来每个代码块在实现上述目标中的作用；
6. 哪些单行代码含有不直观语义，需要局部或行内解释。

只有完整读完当前区域并理解上下文后才能写注释，然后继续向下。不能用“附近已有
中文”“命中了某类 API”或注释数量代替顺序走读。

### 第三阶段：按阅读层次写注释

1. 添加文件职责与边界；
2. 添加主要调用链；
3. 添加数据结构和并发模型；
4. 添加总体方案优缺点。
5. 在函数名上方添加该函数的职责、前置条件和设计说明；
6. 在函数内部按控制流添加“当前阶段在做什么”的代码块说明；
7. 对真正不易理解的语句添加简短行内注释。

三层注释各有职责：背景/设计注释解释“为什么”，代码块注释解释“当前在做什么”，
行内注释解释“这一行的隐藏语义”。不得用其中一层替代另外两层，也不得为了逐行
形式给自解释语句添加注释。

代码块级注释应保持连续覆盖。通常每三到十行、每次状态阶段切换或每个分支都应
重新判断是否需要一段功能说明，避免一个函数只有入口长注释、内部几十行完全没有
走读线索。密度由功能边界决定，不由固定行数或关键字命中数量决定。

### 第四阶段：逐段复核

每完成一个连续源码区域，立即复核：读者是否能不跳到文件其他位置，就理解该段的
背景、输入状态、控制流、输出状态和关键语句。复核通过后才继续下一个区域。

### 第五阶段：全文件验证

1. `git diff --check`；
2. 确认 diff 中没有原始代码或注释删除；
3. 检查宏续行和条件编译结构；
4. 有配置时编译目标对象；
5. 执行函数、英文块、路径、生命周期、关键语句和噪声六项审计；
6. 抽取至少三个复杂函数，从注释独立复述其前置条件、成功路径和失败路径。

## 10. 完成定义

一个文件只有同时满足以下条件才算完成：

- 文件级模型、调用链、数据结构、并发和权衡齐全；
- 函数清单中不存在 `M`；
- 所有核心对象的生命周期闭环；
- fast path、slow path、回滚、释放和并发路径均已覆盖；
- 注释能解释关键代码为何存在，而非仅描述它做了什么；
- 没有批量模板噪声和明显重复；
- 原始代码及注释完整保留；
- 格式检查通过，并在环境允许时完成编译验证。

注释数量不是目标，读者能够借助注释独立、准确地走通源码才是目标。
