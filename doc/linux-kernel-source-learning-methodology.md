# Linux 内核源码学习方法论：文档、详细注释、问题与实验闭环

> 目标：先通过主题文档建立系统认知，再通过详细源码注释理解真实实现；即使读者不熟悉复杂 C 语法和内核调用关系，也能沿注释读懂函数的设计意图、执行过程、状态变化、并发约束与上下游关系。

> 规范边界：本文既描述完整学习闭环，也是向 `.c`/`.h` 源码添加中文学习注释时的主标准和最终
> 验收依据。`./doc/source-code-learning-comments.zh_CN.md` 只作为精简速查清单；两者存在差异时，
> 以本文为准。新会话执行源码注释任务前必须完整阅读本文，不能只读取速查清单。

## 1. 学习目标与现实边界

### 1.1 目标不是逐字翻译源码

详细注释的目标不是把：

```c
p = dup_task_struct(current, node);
```

翻译成：

```text
调用 dup_task_struct，把返回值赋给 p。
```

这种注释只重复了 C 代码，没有解释：

- `current` 是谁；
- `node` 为什么影响分配；
- 返回的新 task 此时是否可见、是否可运行；
- 函数分配了哪些对象；
- 失败时谁负责释放；
- 为什么这一调用必须早于资源复制；
- 该步骤在进程创建宏观地图中的位置。

### 1.2 期望达到的阅读效果

读者读完一个被完整注释的函数后，应能获得一名熟悉该子系统的内核开发者阅读该函数时会主动
恢复出来的上下文：

```text
为什么会调用这个函数
→ 入口时系统处于什么状态
→ 每个关键参数和标志从哪里来
→ 函数经过哪些阶段
→ 每个关键调用把工作交给谁
→ 哪些字段和对象发生变化
→ 当前持有什么锁，能否睡眠
→ ownership 在哪里转移
→ 哪些分支是快速、慢速或失败路径
→ 返回值向调用者承诺什么
→ 返回后下一步通常去哪里
```

### 1.3 “与内核开发者看完代码一样”的可操作定义

多年经验、硬件知识和历史背景无法由一遍注释完全替代，因此不把目标定义为复制某个人的全部
经验，而定义为：**对于当前函数及其所在调用场景，读者能够得到资深开发者完成一次认真 code
review 后应有的局部理解。**

具体表现为读者能够：

- 用自己的话复述函数目的，而不是背函数名；
- 画出调用者、当前函数和主要被调函数的关系；
- 解释关键分支为什么存在；
- 说出主要对象进入和离开函数时的状态；
- 说出每个关键锁、引用和屏障保护什么；
- 识别所有权转移和失败回滚；
- 推测删除某行同步或检查可能产生的错误；
- 在没有逐行注释的相邻函数中继续阅读。

详细注释是认知脚手架。最终目标是逐步减少对脚手架的依赖，而不是让所有代码永久依赖超长注释。

## 2. 四种学习产物的定位

### 2.1 主题 MD：建立森林地图

主题文档负责：

- 历史和技术背景；
- 要解决的问题和核心矛盾；
- Linux 总体方案及其优劣；
- 子系统、对象关系和数据流宏观地图；
- 一个贯穿全文的常见案例；
- 主路径、慢速路径和生命周期；
- 稳定设计不变量；
- 推荐的源码阅读路线；
- 可执行的验证实验。

主题 MD 不负责解释每个局部变量、宏展开和每一行错误跳转。

### 2.2 详细源码注释：解释一棵树如何生长

详细注释直接位于源码附近，负责：

- 当前函数在 MD 宏观地图中的位置；
- 函数调用前置条件和返回保证；
- C 语法、宏和内核惯用法；
- 关键调用的输入、输出和副作用；
- 对象状态和引用所有权变化；
- 锁、并发、RCU 和内存序；
- 快速路径、退化路径和 cleanup；
- 为什么代码顺序不能交换；
- 当前版本特有的实现细节。

详细注释不应重复整篇系统背景。需要宏观背景时链接或指向对应 MD 章节。

### 2.3 问题记录：保存模型断裂

问题文档记录：

- 哪一步没有理解；
- 最初的猜测是什么；
- 通过哪些源码、文档或实验找到证据；
- 最终结论是什么；
- 应把结论补到 MD 还是源码注释；
- 还有哪些未验证假设。

问题记录不是临时聊天记录，而是认知修正过程。

### 2.4 实验：让理解接受现实检验

实验负责验证：

- 调用顺序是否与理解一致；
- 状态变化是否真的可观察；
- 快速路径和慢速路径在什么条件出现；
- 锁竞争、缺页、调度、I/O 延迟发生在哪里；
- 配置和体系结构是否改变结果。

### 2.5 四者关系

```text
主题 MD
告诉读者“系统为什么这样设计，以及完整过程是什么”
       │
       ▼
详细源码注释
告诉读者“当前函数每一步如何实现这个设计”
       │
       ▼
问题记录
暴露“模型与代码之间仍然无法解释的地方”
       │
       ▼
实验与源码证据
验证或推翻当前解释
       │
       └────────→ 回写 MD 或详细注释
```

## 3. 完整学习闭环

### 3.1 第一阶段：阅读主题 MD

第一次只要求建立：

```text
背景
→ 问题
→ 总体方案及优劣
→ 宏观地图
→ 贯穿案例
→ 五个左右的关键不变量
```

此时不要求记住所有函数和字段。

### 3.2 第二阶段：沿主路径读详细注释

例如进程管理第一遍只读：

```text
kernel_clone
→ copy_process
→ wake_up_new_task
→ do_execveat_common
→ begin_new_exec
→ do_exit
→ do_wait
→ release_task
```

第一次可以跳过 audit、perf、LSM、ptrace 冷门分支、fault injection 和不相关配置。

### 3.3 第三阶段：记录问题

遇到以下情况立即记录：

- 看得懂语法，但不知道为什么这样做；
- 理解单行代码，但不知道上下游状态；
- 注释中的结论与代码看起来矛盾；
- 不知道一把锁保护什么；
- 不知道引用在哪获得、在哪释放；
- 不知道某个错误码由谁处理；
- 不知道一个宏实际执行了什么。

### 3.4 第四阶段：带着问题做定向阅读

不要无边界展开所有被调函数。围绕问题选择：

```text
查定义
→ 查所有调用者
→ 查字段的写入者
→ 查锁的获取与释放
→ 查对应 tracepoint
→ 查 Documentation 中的契约
→ 做最小实验
```

### 3.5 第五阶段：回写

结论具有系统普遍性、能帮助理解完整过程：补入主题 MD。

结论只解释某个函数的局部顺序、语法、锁或错误分支：补入源码注释。

结论尚未完全验证：保留在问题记录，不要写成确定事实。

### 3.6 第六阶段：减少注释依赖

完成一个子系统后，选择一个相邻、未详细注释的函数，尝试只依靠：

- 主题 MD；
- 已掌握的不变量；
- 函数签名和调用者；
- 原始内核注释。

若能够自主恢复大部分上下文，说明详细注释真正转化成了源码阅读能力。

## 5. 详细源码注释应达到什么效果

### 5.1 函数头注释必须回答的问题

每个函数都必须在函数声明正上方有中文函数头注释。已有英文 kernel-doc 时，中文函数头放在英文
注释之后，不能用英文参数说明代替中文覆盖。函数头必须说明：

```text
一句话职责
在宏观调用链中的位置
主要调用者
入口前置条件
逐项说明全部入参的业务含义、单位、范围、可空性、输入/输出属性和 ownership
进入时持有的锁/禁用状态
是否可能睡眠
主要执行阶段
逐项说明输出参数在调用前后的内容与 ownership 变化
列出返回值的全部类别：成功值、NULL、布尔值、错误码、错误指针或部分成功
说明不通过返回值表达的字段、全局状态、引用、锁、工作队列或硬件副作用
成功返回保证
失败返回和 ownership
下一步通常由谁继续
当前配置/体系结构差异
```

参数不能用“其余同上”合并省略，也不能只翻译 C 类型。指针参数必须说明是纯输入、输出还是
输入输出，是借用指针还是持有引用，以及调用前后所有权是否改变。

无参数时明确写“入参：无”。返回类型为 `void` 时明确写“返回：无直接返回值”，并继续说明输出
参数和可观察副作用；确实没有出参和副作用时也必须明确写出，不能通过省略让读者猜测。

### 5.2 函数体注释采用“阶段块 + 关键行”

函数头负责契约，函数体负责陪读者沿真实控制流完成走读，两者不能互相替代。除纯 getter、单一
表达式包装和极短 stub 外，函数体必须有连续的阶段说明。

不要每一行都写同等重量的注释。应把准备、校验、查找、获取资源、发布、等待、回滚和释放等状态
阶段写成代码块注释，例如：

```c
/*
 * 阶段 1：稳定 child 身份
 *
 * child 尚未被唤醒，但已发布到 PID 关系。
 * 这里先持有 struct pid，原因是 wake_up_new_task() 后 child
 * 可能立即退出，裸 task_struct 指针不再可靠。
 */
pid = get_task_pid(p, PIDTYPE_PID);
nr = pid_vnr(pid);
```

阶段注释解释过程，行内注释只解释不直观的局部语义。以下位置必须重新提供函数体局部说明：

- 从准备进入执行、从构造进入发布、从正常路径进入回滚等阶段切换；
- 有实际业务含义的 `if`/`switch` 分支，以及分支汇合后的状态；
- 重试、批处理、扫描、等待循环和关键 helper 调用组；
- 锁协议、所有权、对象可见性或硬件状态发生变化的位置；
- 每个 cleanup 标签，说明到达时仍持有哪些资源；
- 不同出口向调用者提供不同保证的返回位置。

密度采用“语义块优先、物理行数兜底”：

- 通常连续 **3～10 行有效代码**构成一个可复述功能块，块前说明当前阶段、目的和完成后状态；
- 连续超过 **10 行有效代码**没有中文走读说明时必须审查；只有纯初始化表、机械重复操作或完全
  自解释的短直线代码可以豁免，并且要能说明原因；
- 超过约 **20 行**或包含两个以上控制流分支的函数，函数体通常不能只有一处中文注释；
- 分支内部再次发生资源、锁、ownership 或状态阶段变化时必须继续拆分。

这些数字是防止注释过疏的下限，不是要求机械地每三行插入注释。验收时隐藏函数头后，读者仍应
能只靠函数体中文注释顺序复述控制流、关键调用、状态变化和失败去向。

### 5.3 注释必须回答“为什么”

每个关键检查、锁、引用和屏障至少回答一个问题：

- 为什么在这里做？
- 为什么必须早于或晚于另一操作？
- 如果省略会发生什么？
- 它与哪个并发路径配对？
- 它把所有权从谁转给谁？

### 5.4 注释必须建立上下游连接

对关键被调函数说明：

```text
调用前传入什么状态
被调函数负责改变什么
返回后当前函数可以假设什么
失败时哪些资源仍归当前函数
```

不能只写“调用 X 完成 Y”，而要说明 X 在整个协议中的边界。

### 5.5 已有注释不可修改，只能在其后补充或修正

源码中原有的任何注释都视为需要保留的历史材料。进行学习型详细注释时，必须遵守：

- 不删除已有注释；
- 不改写已有注释中的任何文字、标点或格式；
- 不移动、合并或拆分已有注释；
- 不用新的中文注释替换原有英文注释；
- 即使已有注释存在错误，也必须原样保留；
- 即使已有注释不完整，也不能直接扩写原注释块。

许可证、版权名单和纯 ASCII 示意图可以不翻译。除此之外，每个英文块注释、单行注释和行尾注释
都必须有可明确对应的紧邻中文内容，不能因为英文很短、函数头已有中文或别处讲过同一概念而跳过。

中文内容必须同时完成：

1. **完整翻译**：忠实覆盖英文原文的对象、动作、因果、条件、警告、限制、TODO/FIXME 和不确定
   语气，不能只概括大意或遗漏限定词；
2. **学习补充**：解释原文默认内核开发者已经知道的背景，以及它在当前函数/分支中的作用、前置
   条件、不变量、并发/ownership 含义和违反后的后果。

翻译和补充可以写在同一个中文块中，不要求添加机械标签。新增注释禁止使用“中文说明：”
“中文学习注释：”“中文解释：”“背景知识：”“逐行学习：”等只标识语言或用途、却不提供
语义的模板前缀；直接写需要传达的行为、约束和原因。该规则只约束后续新增内容，执行新任务时
不为统一风格而回头清理已有标签，除非用户明确要求。简单英文注释的补充可以很短，但必须说明
其在当前过程中的角色，不能只换一种语言复述。原注释错误时，先准确翻译其原意，再用独立
“修正说明”给出当前源码下的结论和证据。

已有注释不够完整时，在它的紧邻下方新增独立注释：

```c
/* 原有注释，必须原样保留。 */

/*
 * 补充说明：原注释只描述了结果；这里还需要说明调用前置条件、
 * ownership 转移以及失败回滚路径。
 */
```

已有注释存在错误或只适用于旧版本、特定架构时，也不得修改原文，而应在紧邻下方明确指出：

```c
/* 原有但已经不准确的注释，仍然原样保留。 */

/*
 * 修正说明：上述说法在当前版本中不完整。当前代码实际通过 ... 保证 ...；
 * 原说法只适用于 ... 配置，证据是 ...。
 */
```

“补充说明”和“修正说明”必须给出源码依据，不能为了保留旧注释而让两个互相矛盾的结论并列、
却不告诉读者哪一个适用于当前版本。该规则的目的，是让学习注释保持可审计：读者可以区分
上游原注释、历史解释和本次新增结论，也能在更新内核版本时准确撤销或重审新增部分。

### 5.6 每个函数、结构体和变量都必须解释用途

详细源码注释不能只覆盖所谓“核心路径”。当前阅读范围内出现的每个函数、结构体和变量，都必须
让初学者知道它为什么存在，以及它在当前过程中的角色。

函数至少说明：

```text
函数解决什么局部问题
谁调用它、它调用谁
入口条件与返回保证
是否持锁、能否睡眠
会修改哪些对象
失败或特殊配置下如何处理
```

结构体至少说明：

```text
结构体代表什么对象或快照
由谁创建、持有、发布和销毁
各字段或字段组分别保存什么
哪些字段受锁、RCU、seqcount 或引用计数保护
哪些字段是派生缓存，必须与哪个源字段同步更新
```

变量包括全局变量、静态变量、函数参数和局部变量。至少说明：

```text
变量保存的业务含义和单位
初始值或哨兵值的含义
由谁写入、由谁读取
变量是借用指针、持有引用还是输出参数
它在哪个阶段有效
它与哪些变量共同构成不变量
```

局部变量不要求全部使用逐行注释，可以在函数入口使用“变量地图”集中解释：

```c
/*
 * 变量地图：
 *   child  新创建 task；当前由创建路径持有，发布前不可运行。
 *   pid    为跨越 child 可能退出的边界而持有的稳定 PID 引用。
 *   retval 当前失败 errno；每个 cleanup 标签原样向外传递。
 *   flags  从 clone 参数解析出的共享/复制策略位图。
 */
```

简单循环计数器、纯粹的临时算术变量也不能完全失去上下文；可以按变量组说明，不必机械地在每个
声明后重复“这是一个整数”。解释重点必须是业务意义、单位、生命周期和相互关系，而不是 C 类型
的中文翻译。

## 6. 面向 C 语法初学者的注释规则

### 6.1 解释影响控制流和所有权的语法

需要解释：

- 指针与多级指针；
- 函数指针和 operation table；
- `container_of`；
- `list_entry`、链表嵌入节点；
- `ERR_PTR/IS_ERR/PTR_ERR`；
- `likely/unlikely`；
- `READ_ONCE/WRITE_ONCE`；
- `cmpxchg`、atomic/refcount；
- `goto` cleanup；
- `__rcu`、`__user`、`__percpu` 等标注；
- `static inline` 和宏生成代码；
- union、柔性数组和位域；
- cleanup class、scope guard 等当前内核惯用法。

不需要反复解释普通 `if`、`for` 和简单赋值，除非其顺序有协议意义。

### 6.2 语法解释必须连接业务语义

错误示例：

```c
if (IS_ERR(p))
    return PTR_ERR(p);
/* IS_ERR 用来判断错误指针。 */
```

推荐示例：

```c
if (IS_ERR(p))
    return PTR_ERR(p);
/*
 * 内核把 -ENOMEM 等负 errno 编码进指针返回值，因此 copy_process()
 * 无需额外输出参数即可同时返回 task 指针或错误。
 * 失败时没有 child 可以唤醒，kernel_clone() 直接把 errno 返回用户态。
 */
```

### 6.3 指针注释要说明所指对象与所有权

对于 `struct task_struct *p`，不能只说“p 是 task 指针”，还应说明：

```text
p 当前指向新 child；
此处由创建路径持有隐含/明确引用；
wake_up_new_task 前 child 尚不能执行；
发布后若跨越可能退出的边界，必须取得 task 或 pid 引用。
```

### 6.4 函数指针要展开分派关系

看到：

```c
file->f_op->read_iter(iocb, iter);
```

注释应说明：

```text
f_op 是 open 时确定的操作表；
普通 ext4 文件、字符设备、procfs 会进入不同实现；
VFS 在调用前已经完成哪些通用检查；
回调必须遵守何种返回与 ownership 约定；
本案例实际会落到哪个实现。
```

### 6.5 `goto` 要画资源回滚栈

不要把 `goto bad_fork_cleanup_mm` 解释成“跳转到标签”。应说明：

```text
当前已经成功取得：task、cred、files、fs、sighand、signal、mm；
namespaces 尚未成功，因此从 cleanup_mm 开始逆序撤销；
每个标签只释放自己对应阶段，并自然落入更早标签；
最终返回 ERR_PTR(retval)。
```

## 7. 函数调用关系的注释规则

### 7.1 每个核心函数提供局部调用地图

```text
调用者：kernel_clone()
          │
          ▼
当前：  copy_process()
          ├── dup_task_struct()
          ├── copy_mm()
          ├── alloc_pid()
          └── copy_thread()
          │
          ▼
返回：未运行、但关系已发布的 child task
下一步：wake_up_new_task()
```

### 7.2 区分 wrapper 与真正状态转换点

源码经常有多层 wrapper。注释必须指出：

```text
syscall wrapper：处理 ABI 和用户参数
通用 helper：处理权限、统计或资源获取
核心状态转换：真正修改队列、页表、对象关系的位置
具体实现回调：文件系统、调度类或驱动代码
```

例如 `fork()` 的关键不是系统调用宏本身，而是 `copy_process()` 的构造/发布与
`wake_up_new_task()` 的调度发布。

### 7.3 对间接调用给出本案例落点

遇到 operation table、调度类或架构 hook 时，注明：

```text
接口定义在哪里；
有哪些常见实现；
当前贯穿案例使用哪一个；
选择实现的条件是什么；
是否可能在运行时替换。
```

### 7.4 控制调用展开深度

只展开能够回答当前问题的调用。判断标准：

```text
它是否改变关键状态？
它是否转移 ownership？
它是否形成发布/提交边界？
它是否可能睡眠或失败？
它是否决定当前案例进入哪条分支？
```

全部为否时，通常只需一句话，不必继续递归展开。

## 8. 状态、所有权和生命周期的注释规则

### 8.1 函数入口和出口状态表

核心函数建议提供：

| 对象 | 入口状态 | 成功出口 | 失败出口 |
|------|----------|----------|----------|
| child task | 不存在 | 已构造/已发布、尚未运行 | 已释放或延迟释放 |
| PID | 未分配 | 已关联 task，调用者可持有引用 | 已归还 namespace |
| mm | parent 所有 | 共享或新 mm | 引用恢复到调用前 |
| runqueue | 无 child | 仍无 child，等待后续 wake | 不变 |

### 8.2 ownership 必须使用明确动词

推荐用词：

```text
借用：不增加引用，不能超出保护范围
持有：已增加引用，必须对应 put
转移：调用成功后释放责任交给被调用方
发布：其他并发查找者开始能够获得对象
摘除：阻止新的查找者获得对象
延迟释放：当前不可达/引用归零，但需等待 RCU 或其他条件
```

避免“处理一下”“设置相关状态”等模糊表达。

### 8.3 标出不可回滚边界

例如 exec：

```text
point_of_no_return = false：失败可返回旧用户程序
point_of_no_return = true：之后错误是 fatal
exec_mmap()：新 mm 所有权转给 current
bprm->mm = NULL：防止 cleanup 再释放已提交 mm
```

### 8.4 标出发布边界

常见发布操作：

- `wake_up_new_task()`：task 开始可运行；
- `fd_install()`：fd reader 可见完整 file；
- `rcu_assign_pointer()`：RCU reader 可见新对象；
- 插入 page cache XArray：并发 fault/read 可找到 folio；
- 写 NVMe SQ doorbell：设备可观察已准备命令。

注释应说明发布前完成了哪些初始化，发布后为何不能再依赖裸指针或本地独占。

## 9. 锁、RCU 与内存序的注释规则

### 9.1 每次加锁说明三件事

```text
保护哪些字段或结构不变量；
与哪个并发路径竞争；
持锁期间允许和禁止什么。
```

错误写法：

```c
spin_lock(&lock); /* 加锁保护 */
```

推荐写法：

```c
/*
 * 与并发 exit_notify()/fork 发布竞争，保护 parent、children 和 PID 链接
 * 的结构性修改。持有 tasklist_lock write side 期间不能执行可能长时间
 * 睡眠的资源释放，因此 release_task() 把部分工作延后到出锁后。
 */
write_lock_irq(&tasklist_lock);
```

### 9.2 RCU 注释必须区分两种保证

```text
读取一致性：通过 rcu_dereference、seqcount 或重新验证获得
生命周期：  grace period 保证对象内存暂不释放
```

RCU 不自动冻结对象内容，也不允许退出临界区后继续使用裸指针。

### 9.3 内存屏障必须写出配对关系

注释至少给出：

```text
本 CPU 在屏障前发布什么；
另一 CPU 在哪条路径观察；
配对的 acquire/release/lock/barrier 在哪里；
允许重排时会产生什么错误。
```

例如等待—唤醒：条件写、task state 写和状态读取若重排，可能双方都看不到对方更新，造成 lost
wakeup。只写“保证内存顺序”不算解释完成。

### 9.4 引用计数不是锁

详细注释要明确：引用保证对象不释放，不保证字段不变化；锁保证特定状态转换，不自动延长对象
生命周期；RCU 保护读侧窗口，也不等于获得长期引用。

## 10. 宏、内联函数和条件编译的处理

### 10.1 宏必须解释实际效果

遇到复杂宏时给出等价伪代码，但不要假装它是精确展开：

```text
SYSCALL_DEFINE3(execve, ...)
大致生成体系结构可见 syscall wrapper、类型检查和内部实现入口。
本节关注参数进入 do_execveat_common() 后的语义，不展开 syscall 元编程细节。
```

### 10.2 当前内核 cleanup class

遇到 `CLASS(...)`、guard 或自动 cleanup，需要说明：

- 变量离开作用域时自动调用哪个析构；
- 成功时如何 `take/retain` 取消自动释放；
- 它替代了哪类 goto cleanup；
- ownership 是否真的合并，还是只让回滚结构化。

### 10.3 条件编译必须指出当前讨论配置

```text
CONFIG_PREEMPT_RCU=y 时走哪条路径；
关闭时读锁语义有何不同；
本文主线使用哪个配置；
另一配置保留什么设计不变量。
```

不要把某个 `#ifdef` 下的实现写成所有内核都具备的行为。

### 10.4 内联函数何时继续展开

如果 inline 只是字段读取，可以直接解释结果；如果它包含 barrier、引用获取、状态转换或体系结构
指令，应继续展开并说明隐藏语义。

## 11. 一个函数的完整注释模板

```c
/*
 * function_name() - 一句话职责
 *
 * 【宏观位置】
 * caller_a() → function_name() → callee_b()
 * 对应主题文档“某某阶段”。
 *
 * 【为什么需要】
 * 最简单方案有什么竞态、性能或语义问题，本函数如何解决。
 *
 * 【入口条件】
 * - 当前上下文：进程/中断/softirq；能否睡眠
 * - 已持有的锁、RCU、引用
 * - 关键对象状态
 *
 * 【参数】
 * @p: 指向什么对象；借用还是持有；调用期间能否变化
 * @flags: 哪些位影响本案例，来源是什么
 *
 * 【主要阶段】
 * 1. 验证并稳定输入
 * 2. 执行快速路径
 * 3. 必要时退化到慢速路径
 * 4. 发布状态或转移 ownership
 * 5. 失败时逆序回滚
 *
 * 【成功出口】
 * 返回值、对象状态、所有权、调用者下一步。
 *
 * 【失败出口】
 * errno、已释放/仍需释放的资源、是否可重试。
 *
 * 【并发不变量】
 * 哪些锁、引用、RCU 或屏障保证什么；删除后会怎样。
 */
```

函数体按阶段插入块注释。只有语法不直观或顺序关键的行使用行内注释。

## 12. 注释示例：wait 如何唯一领取 zombie

原始核心代码：

```c
state = (ptrace_reparented(p) && thread_group_leader(p)) ?
        EXIT_TRACE : EXIT_DEAD;
if (cmpxchg(&p->exit_state, EXIT_ZOMBIE, state) != EXIT_ZOMBIE)
    return 0;
```

面向本学习目标的注释：

```c
/*
 * 正常 parent 收尸后进入 EXIT_DEAD；如果 ptrace 改写了父子关系，
 * tracer 先领取为 EXIT_TRACE，之后还可能把死亡事件交还真实 parent。
 * 三目运算符的结果只是目标状态，此时尚未修改 p。
 */
state = (ptrace_reparented(p) && thread_group_leader(p)) ?
        EXIT_TRACE : EXIT_DEAD;

/*
 * cmpxchg(address, old, new) 的语义：
 *   如果 *address == old，则原子写入 new；无论成功失败都返回旧值。
 *
 * 多个父线程可以同时 wait 同一个 child。只有一个线程能成功把
 * exit_state 从 EXIT_ZOMBIE 改为 EXIT_DEAD/EXIT_TRACE；成功者取得
 * 唯一收尸权，随后可以在释放 tasklist_lock 后汇总统计并 release_task。
 *
 * 失败表示另一个 waiter 已经领取。这里不能使用普通的
 *   if (p->exit_state == EXIT_ZOMBIE) p->exit_state = state;
 * 因为检查和写入之间存在竞态，两个 waiter 可能同时认为自己成功，
 * 导致退出统计累计两次、release_task() 执行两次和 use-after-free。
 */
if (cmpxchg(&p->exit_state, EXIT_ZOMBIE, state) != EXIT_ZOMBIE)
    return 0;
```

这段注释同时完成：

- 三目运算符语法解释；
- `cmpxchg` 语义解释；
- 并发参与者说明；
- 状态转换说明；
- 为什么不能用普通赋值；
- 成功后 ownership 说明；
- ptrace 分支的业务原因。

这才是“读一遍注释获得开发者阅读上下文”，而不是逐字翻译。

## 14. 实验验证的定位和格式

每个实验至少说明：

```text
要验证的结论
最小程序或命令
所需内核配置/权限
预期事件顺序
对应源码位置
结果不符合预期时的可能原因
实验不能证明什么
```

例如 tracepoint 看到 `sched_process_exit`，只能证明 task 进入了退出路径，不能证明 parent 已 wait，
更不能证明 task_struct 已经释放。实验结论必须严格限定在观测能力内。

实验按难度分层：

1. 用户行为：strace、procfs；
2. 子系统事件：tracepoint、perf；
3. 函数和状态：ftrace、kprobe/eBPF；
4. 修改验证：debug config、fault injection、临时 trace；
5. 崩溃后分析：crash、drgn、vmcore。

## 15. 三遍源码阅读法

### 15.1 第一遍：只看控制骨架

目标：知道函数分几阶段，成功和失败各走哪里。

关注：

- 函数头注释；
- 主 `if/switch`；
- 核心被调函数；
- return 和 goto labels；
- 发布/提交点。

暂时跳过复杂统计、调试和边缘配置。

### 15.2 第二遍：看状态与 ownership

目标：知道每阶段改变了什么。

关注：

- 关键字段写入；
- 引用增加/减少；
- 入队/出队；
- 指针发布/摘除；
- cleanup 逆序；
- 返回值和错误指针。

### 15.3 第三遍：看并发正确性

目标：理解为什么顺序和同步不可改变。

关注：

- 锁顺序；
- RCU 临界区；
- seqcount 验证；
- atomic/cmpxchg；
- READ_ONCE/WRITE_ONCE；
- acquire/release/barrier 配对；
- 与退出、唤醒、回收和热插拔的竞态。

### 15.4 每遍完成检查

```text
第一遍：能否用 5～15 个节点画出调用过程？
第二遍：能否画出关键对象的入口/出口状态？
第三遍：能否解释至少一个竞态，以及删除同步后的后果？
```

## 16. 如何从一个函数扩展到整个子系统

不要按文件从第一行读到最后一行。推荐沿“垂直路径 + 横向协议”扩展。

### 16.1 垂直路径

从用户入口跟到完成：

```text
fork → task 构造 → 调度 → exec → exit → wait
write → page cache → writeback → bio → blk-mq → NVMe → completion
open → path walk → dentry/inode → file → fd install
```

### 16.2 横向协议

再围绕关键对象查所有状态操作：

```text
谁写 p->__state？
谁增加/减少 file->f_ref？
谁设置/清除 folio writeback？
谁修改 dentry d_parent，并如何让 RCU reader 发现？
谁分配/释放 request tag？
```

垂直路径建立过程，横向协议证明对象在所有入口下都保持不变量。

### 16.3 扩展停止条件

当被调函数只实现已理解的通用操作，且不改变当前问题的状态、ownership 或并发边界时，可以停止
展开。避免一次问题把阅读扩散到整个内核。

## 17. 详细注释的质量验收标准

### 17.1 函数级硬性门槛

- [ ] 有一句话职责和宏观调用位置；
- [ ] 说明主要调用者和后续去向；
- [ ] 说明入口锁、上下文和是否可睡眠；
- [ ] 逐项解释全部入参的业务语义、单位、范围、可空性、输入/输出属性和 ownership；
- [ ] 逐项说明输出参数、返回值全部类别、ownership 变化及其他可观察副作用；
- [ ] 无参数、`void` 或无副作用时也有明确说明；
- [ ] 把函数划分为可复述的阶段；
- [ ] 函数体对阶段切换、重要分支、循环、helper 调用组和 cleanup 标签持续提供走读说明；
- [ ] 超过十行的无中文区段有明确豁免理由，复杂函数不是只有函数头注释；
- [ ] 解释关键 C 语法和内核惯用法；
- [ ] 每个关键被调函数说明输入、输出和副作用；
- [ ] 展示关键字段或对象的状态变化；
- [ ] 标出引用获得、转移和释放；
- [ ] 标出发布点或不可回滚边界；
- [ ] 说明快速路径、慢速路径和失败路径；
- [ ] 对 goto cleanup 说明已经取得的资源和逆序释放；
- [ ] 对关键锁说明竞态双方和保护对象；
- [ ] 对 RCU/屏障说明保证范围和配对路径；
- [ ] 说明成功与失败返回后调用者可假设什么；
- [ ] 所有结论已与当前版本源码核对。
- [ ] 已有注释逐字保留；错误或缺失只通过紧邻其后的独立“修正说明/补充说明”处理；
- [ ] 每个非豁免英文注释都有紧邻的完整中文翻译和学习补充，未只做摘要或远处笼统覆盖；
- [ ] 每个函数都有用途、调用关系、入口条件和返回语义说明。
- [ ] 每个结构体及其字段或字段组都有角色、生命周期和同步规则说明。
- [ ] 每个全局、静态、参数和局部变量都有业务含义、单位、所有权或有效阶段说明。

### 17.2 初学者可读性测试

读者在不预先熟悉该函数的情况下，读完注释后应能回答：

1. 为什么调用它？
2. 输入对象现在归谁所有？
3. 函数分哪几个阶段？
4. 最重要的三个被调函数分别负责什么？
5. 哪一行真正改变了外界可观察状态？
6. 失败会撤销哪些已经完成的工作？
7. 哪个并发路径会与它竞争？
8. 为什么某个锁、原子操作或屏障不能删除？
9. 返回后下一步通常是什么？
10. 本函数在主题 MD 的宏观地图中位于哪里？

回答不了的问题，说明注释仍有认知缺口。

### 17.3 开发者视角测试

注释应允许读者完成以下推理：

```text
改变调用顺序是否破坏不变量？
新增错误返回时应该跳到哪个 cleanup label？
某个对象能否在释放锁后继续使用？
某个回调是否允许睡眠？
同一函数在另一配置下会进入什么分支？
tracepoint 应放在发布之前还是之后？
```

这比“能逐行说出代码做什么”更接近内核开发者的阅读效果。

## 18. 常见失败方式

### 18.1 逐行中文翻译

症状：注释很多，但删除注释后读者仍不知道函数目的和状态变化。

修正：用阶段块组织，重点解释原因、不变量和上下游契约。

### 18.2 在每个函数重复完整背景

症状：源码被巨量重复注释淹没，后续难以维护。

修正：宏观背景放 MD；函数头只写当前位置并引用主题章节。

### 18.3 无限展开调用

症状：为了理解一个函数，递归注释几十个不相关 helper，主线消失。

修正：围绕问题展开，只追踪状态、ownership、发布、失败和并发边界。

### 18.4 只解释正常路径

症状：成功流程清楚，但不知道资源由谁释放，也不知道错误码如何返回。

修正：为每个资源建立 acquire/release 对，并画 cleanup stack。

### 18.5 把推测写成事实

症状：使用“应该是”“可能为了性能”，却没有源码或实验依据。

修正：未验证内容进入问题记录；确定结论注明源码和配对路径。

### 18.6 注释与代码版本脱节

症状：函数已改名、锁已移除、CFS 已变为 EEVDF，注释仍描述旧实现。

修正：标注分析 commit；代码变化时同步检查附近注释和主题 MD。

### 18.7 解释语法却不解释业务

症状：读者知道 `cmpxchg` 是原子比较交换，却不知道它在防止两个 waiter 同时收尸。

修正：所有语法解释都必须落回当前对象、竞态和状态转换。

## 19. 目录组织与维护规则

推荐组织：

```text
doc/
├── linux-kernel-internals-writing-guide.md
├── linux-kernel-source-learning-methodology.md
├── 08 linux-process-management-internals.md
├── 09 linux-memory-management-internals.md
├── ...
└── questions/
    ├── process-management-questions.md
    └── ...

源码目录：
kernel/fork.c        保留函数局部详细注释
fs/exec.c
kernel/exit.c
...
```

### 19.1 结论放在哪里

| 内容 | 存放位置 |
|------|----------|
| 历史、问题、总体设计、方案优劣 | 主题 MD |
| 宏观地图、贯穿案例、端到端过程 | 主题 MD |
| 局部变量、宏、关键调用、锁和 cleanup | 源码注释 |
| 尚未证实的疑问和推理过程 | questions 文档 |
| 验证脚本和预期结果 | 主题 MD 或独立实验目录 |

### 19.2 更新顺序

源码版本变化时：

1. 检查函数签名和调用关系；
2. 更新源码局部注释；
3. 判断宏观设计是否改变；
4. 只有设计或主路径改变时才更新主题 MD；
5. 保留有价值的版本差异说明，删除已失效事实。

### 19.3 注释不能改变代码行为

纯学习注释修改后仍应：

- 通过格式检查；
- 不改变预处理结果；
- 不破坏 kernel-doc 格式；
- 不在宏续行中插入非法注释；
- 不改变 `__init`、section、attribute 或条件编译关联；
- 必要时完成原有构建/静态检查。

### 19.4 注释修改必须是追加式的

完成源码补注后，应单独审计 diff：已有注释不得出现删除或改写。允许的变化只有在原代码或
原注释附近新增独立注释。若必须纠正已有注释，保留原文，并在其紧邻下方追加带有当前版本
证据的“修正说明”；若只是信息不足，则追加“补充说明”。

验收时不能只检查“可执行代码是否相同”，还要检查：

```text
原有注释删除行数 = 0
原有注释改写行数 = 0
修正内容能够与被修正注释直接对应
补充内容没有伪装成上游原注释的一部分
```

## 20. 最终学习完成标准

对一个主题达到“完整理解”，至少应能够：

- 不看文档画出背景、问题、方案和宏观地图；
- 用贯穿案例复述端到端主路径；
- 独立找到用户 API 对应的内核入口；
- 解释主要数据结构为什么存在，而不只是字段含义；
- 说明关键函数入口条件、阶段和返回保证；
- 追踪主要对象的状态与 ownership；
- 解释至少一个快速路径退化过程；
- 解释至少一个失败回滚过程；
- 解释至少一个具体并发竞态和同步配对；
- 说明方案优点、代价和适用边界；
- 用实验验证两个以上关键结论；
- 阅读一个相邻、未详细注释的函数并恢复其上下文；
- 向另一位初学者讲清楚，而不依赖背诵函数名。

最终方法可以概括为：

```text
MD 建立森林地图
→ 详细注释恢复开发者阅读上下文
→ 问题记录暴露模型断裂
→ 源码和实验建立证据
→ 回写形成更准确的下一轮起点
→ 在相邻代码中逐渐脱离详细注释
```

判断学习是否成功的标准，不是“注释了多少行”，而是读者面对新的内核代码时，能否主动寻找：

```text
它解决什么问题？
它处于哪条调用链？
哪些对象发生状态变化？
谁拥有这些对象？
什么同步保证并发正确？
失败如何回滚？
完成后如何验证？
```

当这些问题成为阅读代码时的自然反应，详细注释就完成了它的使命。
