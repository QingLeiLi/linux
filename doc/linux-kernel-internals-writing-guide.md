# Linux 内核机制文档写作规范

> 目标：编写能够帮助读者真正理解 Linux 内核设计与源码实现的机制分析文档，而不是结构体、函数和概念的平铺罗列。

---

## 1. 核心原则

一篇内核机制文档必须回答以下问题：

1. 这个机制是在什么背景下产生的？
2. 它要解决的核心矛盾是什么？
3. 最直观的方案为什么不够？
4. Linux 最终选择了什么技术方案？
5. 这个方案在真实场景中如何运行？
6. 源码中的数据结构和函数如何共同证明这一过程？
7. 方案获得了什么收益，又付出了什么代价？
8. 并发、失败和资源回收时如何保持正确？
9. 如何通过 trace、日志或实验观察和验证？
10. 读者能否在进入细节前看到完整的宏观地图？

文档的目标不是让读者记住更多函数名，而是帮助读者建立一套可以解释源码行为的模型。

---

## 2. 由浅入深，而不是直接进入源码

### 2.1 从用户能够观察的现象开始

开头应选择一个常见现象或操作。例如：

```text
为什么 fork() 一个占用数 GB 内存的进程通常很快？
为什么 unlink() 文件后，已经打开的 fd 仍然能够读取？
为什么系统还有大量可回收缓存，却会出现直接内存回收延迟？
为什么任务已经被唤醒，却没有立即获得 CPU？
```

这些问题为后续源码分析提供明确目标。读者每学习一个内核对象，都能知道它在解决案例中的哪一部分问题。

### 2.2 推荐的认知层次

```text
用户可见行为
    ↓
需要满足的语义
    ↓
最简单的实现方案
    ↓
简单方案的问题
    ↓
Linux 的总体技术方案
    ↓
宏观地图：子系统边界、对象关系和主调用阶段
    ↓
核心数据结构
    ↓
真实调用过程
    ↓
并发、异常和回收路径
    ↓
性能收益与工程代价
```

不要在读者尚不知道“为什么需要它”时，直接罗列一个大型结构体的所有字段。

### 2.3 每深入一层都要说明原因

错误写法：

```text
VFS 使用 dentry cache。dentry 中包含 d_parent、d_inode 和 d_seq。
```

推荐写法：

```text
路径解析会重复访问相同目录。如果每次 open() 都让文件系统重新读取目录，
本地磁盘会产生额外 I/O，网络文件系统还会产生远程请求。

因此 VFS 缓存“父目录 + 名字 → inode”的查询结果，这就是 dentry。
缓存不仅保存存在的文件，还保存“这个名字不存在”的 negative dentry，
从而避免重复执行失败查询。

缓存又带来 rename 并发问题：无锁读者如何确认 d_parent 和 d_name 没有变化？
这才需要 d_seq，使 RCU-walk 可以在读取后验证快照是否仍然有效。
```

## 3. 先讲背景和矛盾，再给出 Linux 方案

### 3.1 用方案演进帮助读者理解设计

一个机制应尽量按照设计推导展开：

```text
方案 A：最容易想到的实现
  优点：简单，正确性容易证明
  问题：在哪种负载或并发规模下无法接受

方案 B：针对性能问题进行改进
  优点：解决了哪个瓶颈
  新问题：引入了什么一致性或生命周期问题

Linux 方案：如何组合快速路径、慢速路径和回退机制
```

例如解释 per-CPU runqueue：

```text
全局 runqueue：
  所有 CPU 都能看到完整任务集合，容易选择全局最优任务。
  但每次唤醒、阻塞和调度都争用同一把锁。

per-CPU runqueue：
  本地调度只锁本 CPU，扩展性更好。
  但系统失去了始终精确的全局负载视图。

Linux 的组合方案：
  per-CPU rq 负责高频本地操作；
  wakeup placement 决定新唤醒任务的位置；
  newidle balance 在 CPU 空闲时主动拉取任务；
  periodic balance 修正长期不均衡；
  active balance 处理普通迁移无法解决的严重失衡。
```

这样读者能理解每条复杂路径为何存在，而不是把它们当作互不相关的函数。

### 3.2 明确核心矛盾

常见内核设计矛盾包括：

- 吞吐量与响应延迟；
- 全局最优与局部无锁；
- 缓存命中与一致性；
- 立即释放与无锁读者安全；
- 精确记账与热路径成本；
- 物理连续性与分配成功率；
- 公平性与交互任务唤醒延迟；
- 强隔离与资源共享效率。

一篇文章应明确指出它主要处理哪几个矛盾。

### 3.3 进入细节前必须给出宏观地图

宏观地图的作用是让读者知道后续代码处于系统的什么位置。它至少应包含三层：

```text
子系统边界：哪些模块参与，它们分别负责什么
对象关系：  核心对象由谁持有、共享和索引
过程阶段：  请求从入口到完成经历哪些发布或提交点
```

例如进程管理可以先画成：

```text
fork.c              exec.c             exit.c
创建 task           替换程序映像       释放运行资源
   │                    │                  │
   ├──── PID/父子/线程组关系 ──────────────┤
   ├──── mm/files/cred/ns 等资源对象 ──────┤
   └──── sched_fork → runnable → task_dead ┘
```

宏观地图不等于罗列完整调用链。它应保持小而稳定，只展示理解后文所需的边界和主数据流；函数级
调用、锁和异常分支留到对应章节展开。后文出现新的对象或路径时，应明确指出它位于地图中的哪一层。

## 4. 必须使用一个常见案例贯穿全文

### 4.1 案例不是最后的附录

案例应该从文章开头出现，并在每个关键章节继续推进。不能先用几十页罗列知识点，最后才附上一条与正文脱节的调用链。

例如 VFS 文档可以使用：

```c
int fd = open("/tmp/demo", O_CREAT | O_RDWR, 0644);
write(fd, "hello", 5);
lseek(fd, 0, SEEK_SET);
read(fd, buf, 5);
unlink("/tmp/demo");
close(fd);
```

围绕它依次回答：

1. `/tmp/demo` 如何解析？
2. dcache 未命中时谁去查找具体文件系统？
3. `O_CREAT` 如何避免两个线程同时创建成功？
4. fd 槽位和 `struct file` 为什么分两个阶段发布？
5. `write()` 为什么通常没有立即访问磁盘？
6. `read()` 如何命中刚写入的 page cache？
7. unlink 后为什么 fd 仍然有效？
8. close 后 inode 和数据块何时真正释放？

### 4.2 案例选择标准

贯穿案例应满足：

- 用户经常遇到，容易建立直觉；
- 能覆盖该机制的主要对象和路径；
- 正常路径不过度复杂；
- 可以自然引出至少一个并发或异常问题；
- 能够使用 trace、procfs 或简单程序验证。

### 4.3 不要为覆盖所有功能而扭曲案例

案例用于建立主线，不需要强行容纳所有扩展功能。NUMA、cgroup、热插拔、安全机制等内容可以在主线模型建立后作为分支展开。

## 5. 通过状态变化讲解过程

### 5.1 数据结构必须放在过程中理解

与其单独列出字段，不如展示一次操作如何改变它们。

例如任务睡眠和唤醒：

```text
运行中：
  __state = TASK_RUNNING
  on_rq   = 1
  on_cpu  = 1

准备等待：
  set_current_state(TASK_INTERRUPTIBLE)
  加入 wait queue
  再次检查等待条件

进入 __schedule()：
  条件仍不满足
  → dequeue_task()
  → on_rq = 0
  → context switch
  → on_cpu = 0

事件发生：
  try_to_wake_up()
  → TASK_INTERRUPTIBLE → TASK_WAKING
  → 选择目标 CPU
  → enqueue_task()
  → TASK_RUNNING
  → on_rq = 1
```

状态变化能同时解释字段含义、函数顺序和并发约束。

### 5.2 标出对象所有权变化

例如 open：

```text
开始：
  没有 fd，也没有 file

get_unused_fd_flags()：
  open_fds[fd] = 1
  fd[fd]       = NULL
  含义：fd 已被保留，但其他线程还不能获得 file

do_file_open()：
  完成路径解析
  初始化 f_path、f_inode、f_op、f_mode

fd_install()：
  rcu_assign_pointer(fd[fd], file)
  含义：完整 file 正式发布

失败回滚：
  put_unused_fd(fd)
  fput(file)
```

### 5.3 区分逻辑状态与物理状态

很多内核机制存在多个状态维度：

- task 的 `__state`、`on_rq`、`on_cpu`；
- folio 的 referenced、dirty、writeback、mapped、LRU；
- inode 的 link count、引用计数、cache 状态；
- dentry 的 positive/negative、hashed/unhashed、referenced；
- RCU 对象的不可达、引用归零和真正释放。

不能把这些维度压缩成一个过度简化的线性状态机。

## 6. 代码必须参与论证

### 6.1 代码引用的目的

引用代码是为了证明以下内容之一：

- 调用顺序；
- 状态转换；
- 锁和内存屏障；
- 引用所有权；
- 快速路径和慢速路径的分支条件；
- 失败回滚顺序；
- 配置选项导致的实现差异。

不要只贴出大段源码后逐行翻译。

### 6.2 推荐的代码讲解方式

先提出结论：

> 新文件必须完全初始化后才能被并发 fd reader 看到。

再引用最小相关代码：

```c
rcu_assign_pointer(fdt->fd[fd], file);
```

然后解释它证明了什么：

```text
fd 分配阶段只设置 open_fds bit，并不发布 file 指针。
路径解析和 f_op->open 全部成功后，fd_install() 才执行 release store。
RCU reader 一旦读取到非 NULL file，就能看到发布之前完成的初始化写入。
```

最后说明缺少该协议会怎样：

```text
如果先写入 fd[fd]，再初始化 f_op，另一个线程可能通过同一 fd 进入 read()，
观察到尚未初始化的 operation table。
```

### 6.3 控制代码长度

一次引用只保留能支持结论的字段或分支。大函数应先画调用骨架，再分别分析关键片段：

```text
try_to_wake_up()
  → 状态匹配
  → 等待 on_cpu 清除
  → 选择目标 CPU
  → 本地或远端入队
  → 判断是否抢占
```

之后只引用与每个结论有关的几行代码。

### 6.4 使用当前源码名称

写作前必须在当前仓库中核对：

- 函数是否仍然存在；
- 是否被重命名或拆分；
- 数据结构字段是否改变；
- 调用路径是否引入新的 cleanup、folio、Maple Tree 或 EEVDF 机制；
- 配置条件是否改变默认行为。

例如当前调度器不应继续写成“红黑树按 vruntime 排序并选择最左节点”，因为当前 fair class 使用 EEVDF，树按 virtual deadline 排序，并使用子树 `min_vruntime` 判断 eligibility。

## 7. 必须分析方案的优点和代价

### 7.1 每个重要机制都要完成闭环

推荐使用以下格式：

```text
解决的问题：
  为什么需要这个机制？

核心方案：
  Linux 如何实现？

收益：
  热路径减少了什么开销？
  提供了什么语义？

代价：
  增加了哪些状态、锁、内存占用或慢速路径？

退化条件：
  哪些情况下快速路径不能工作？

替代方案：
  为什么没有选择更直观的方案？
```

### 7.2 示例：RCU path walk

```text
解决的问题：
  路径解析每经过一个 dentry 都修改引用计数，会造成多核 cacheline 争用。

方案：
  在 RCU 临界区内读取 dentry 和 mount，使用 d_seq、mount sequence 验证快照。

收益：
  dcache 命中的普通路径不需要逐层 dget/mntget。

代价：
  读路径不能随意睡眠；rename、mount 和 dentry 生命周期需要 sequence 与 RCU 配合。

退化：
  需要阻塞、缓存未命中或 sequence 验证失败时，返回内部 -ECHILD，重走 REF-walk。

替代方案的问题：
  始终使用全局锁或逐层引用虽然简单，但高并发 pathname lookup 扩展性差。
```

### 7.3 不要把“复杂”作为唯一缺点

代价应尽量具体：

- 增加几次原子操作或 cacheline bouncing；
- 需要跨 CPU IPI；
- 造成 TLB shootdown；
- 增加内部碎片；
- 需要保存额外元数据；
- 延长失败路径；
- 牺牲短期公平或缓存局部性；
- 产生近似统计误差；
- 需要后台线程和延迟回收。

## 8. 快速路径、慢速路径和回退路径必须一起讲

内核性能通常来自“常见情况很快，少见情况保证完整语义”。因此不能只讲理想快速路径。

推荐结构：

```text
快速路径：
  前置条件是什么？
  为什么不需要睡眠或全局锁？

快速路径失败：
  哪个检查发现无法继续？
  返回值或状态如何表达？

慢速路径：
  会取得哪些锁？
  是否调用文件系统、设备或远端 CPU？
  如何重新验证快速路径期间观察的状态？

失败回滚：
  已经取得的对象按什么顺序释放？
```

常见例子：

- RCU-walk → REF-walk；
- page cache hit → 分配 folio 并提交 I/O；
- per-CPU page list → buddy → reclaim/compaction/OOM；
- 本地 wakeup → 远端 wake list/IPI；
- slab per-CPU fast path → node partial → buddy；
- optimistic spinning → mutex sleep queue。

## 9. 并发分析必须具体到竞态窗口

### 9.1 不要只写“这里需要加锁”

应说明：

1. 哪两个或多个执行上下文并发？
2. 它们分别读写什么状态？
3. 没有同步时会出现什么错误结果？
4. 哪把锁、引用或内存屏障关闭了窗口？
5. 该机制保护的是对象内容还是对象生命周期？

### 9.2 示例：丢失唤醒

```text
waiter CPU                       waker CPU
检查 condition == false         condition = true
设置 TASK_INTERRUPTIBLE         检查 task state
schedule()                       未发现可唤醒状态
```

如果检查条件和发布睡眠状态顺序错误，事件可能已经发生，但 waiter 永久睡眠。

正确协议：

```text
waiter 先加入等待队列并发布睡眠状态
→ 再检查 condition
→ waker 先更新 condition
→ 再 wake_up
→ 两侧通过锁或内存屏障保证至少一方看到另一方更新
```

### 9.3 区分锁、引用计数和 RCU

- 锁：保护并发状态转换与结构不变量；
- 引用计数：保证持有者使用期间对象不被释放；
- RCU：允许无锁读者访问旧版本，并推迟回收；
- seqcount：检测读取期间是否发生变化，但本身通常不保证对象生命周期；
- memory barrier：约束不同 CPU 对状态发布和观察的顺序。

不要笼统地写成“通过 RCU 保证线程安全”。

## 10. 正常路径、失败路径与回收路径同等重要

### 10.1 内核机制通常是分阶段提交

例如进程创建：

```text
构造阶段：
  分配 task_struct、内核栈、资源对象和 PID
  新任务尚不可运行

发布阶段：
  挂入父子、线程组和 PID 关系
  wake_up_new_task() 后可被其他 CPU 运行

失败阶段：
  按初始化的相反顺序经过 bad_fork_cleanup_* 回滚
```

文档应指出不可回滚边界、发布点和失败清理顺序。

### 10.2 释放不等于立即销毁

很多内核对象遵循：

```text
从名字空间或索引中摘除
→ 阻止新的查找者
→ 等待已有引用归零
→ 等待并发读者或硬件状态失效
→ 最终释放内存
```

典型例子：

- unlink 后的 inode；
- close 后的 `struct file`；
- 退出后的 zombie task；
- 页表清除后的 TLB invalidation；
- dentry/task/PID 的 RCU 延迟释放。

## 11. 用实验和观测完成论证

### 11.1 每篇文档至少提供一个可验证实验

实验应包含：

- 最小复现程序或命令；
- 预期观察结果；
- 对应的 tracepoint/procfs/debugfs；
- 如何把结果映射回源码路径；
- 可能影响结果的配置和版本差异。

### 11.2 示例：验证 unlink 生命周期

```bash
exec 3<>/tmp/demo
printf hello >&3
rm /tmp/demo
ls -l /proc/$$/fd/3
cat <&3
```

预期结果：

```text
/tmp/demo 路径已经不存在；
/proc/<pid>/fd/3 显示文件带有 (deleted)；
fd 仍持有 struct file/path/inode，所以仍能读取；
关闭 fd 后，最后引用消失，文件系统才有机会最终释放 inode 和数据块。
```

### 11.3 调试信息不能只列命令

每个命令应说明观察什么：

```text
/proc/<pid>/sched：区分运行时间、等待时间和迁移；
/proc/<pid>/smaps_rollup：区分 RSS、PSS、匿名页和文件页；
/proc/<pid>/fdinfo：观察 file position 和 fd flags；
sched_wakeup → sched_switch：计算 wake-to-run latency；
filemap fault trace：区分 page cache hit 与存储 I/O。
```

## 12. 推荐的文章结构

```text
# 标题

> 内核版本、主要源码目录和分析范围

## 1. 一个常见问题
给出贯穿全文的程序、命令或系统现象。

## 2. 背景和核心矛盾
说明简单方案、规模扩大后的问题，以及必须满足的语义。

## 3. Linux 的总体方案
说明核心策略，并集中比较方案的优点、代价、适用边界和退化条件。

## 4. 宏观地图
进入源码前画出子系统边界、关键对象关系和端到端阶段；只出现后续主线需要的节点。

## 5. 核心对象
围绕案例介绍对象关系，不罗列无关字段。

## 6. 案例的快速路径
沿当前源码给出完整调用骨架。

## 7. 关键阶段源码分析
每节采用“结论 → 最小代码 → 状态变化 → 为什么正确”。

## 8. 慢速路径和失败回滚
解释快速路径的边界与退化条件。

## 9. 并发与生命周期

## 10. 方案收益、代价和适用边界

## 11. 观测实验
用可运行方法验证文章中的核心结论。

## 12. 回到开头案例
把每个用户可见结果映射到内核状态变化。

## 13. 关键函数索引
作为阅读源码入口，而不是正文替代品。
```

## 13. 单节写作模板

每个重要机制可以使用以下模板：

```markdown
### 机制名称

#### 它解决的问题

描述具体负载、语义或竞态，不使用空泛表述。

#### 最简单方案及其问题

说明为什么不能只使用全局锁、立即复制、同步 I/O等直观方案。

#### Linux 的实现

给出对象关系和 5～15 行调用骨架。

#### 关键源码

只引用支持结论的代码，并注明当前源码位置。

#### 状态变化

展示操作前、操作中和操作后的字段、引用或队列状态。

#### 并发正确性

说明竞态双方、锁、引用、RCU 和内存序。

#### 优点与代价

说明快速路径收益、额外复杂度和退化条件。

#### 在贯穿案例中的作用

回到开头示例，解释用户最终观察到什么。
```

## 15. 应避免的写法

### 15.1 结构体字段百科

```text
struct foo 有字段 A、B、C、D……
```

如果没有说明字段在哪个过程中被读写、由谁保护以及解决什么问题，字段列表只能作为附录。

### 15.2 只有函数箭头

```text
A() → B() → C() → D()
```

调用链必须补充：每一步输入什么状态、修改什么对象、何时可能阻塞、失败后退回哪里。

### 15.3 只有正确结论，没有设计原因

```text
Linux 使用 per-CPU cache 提升性能。
```

需要继续解释共享 cache 的具体争用、per-CPU cache 带来的批量 refill、内存不均衡和回收代价。

### 15.4 用“为了性能”结束分析

性能必须具体到：减少锁竞争、避免 I/O、降低 TLB miss、减少 cacheline bouncing、批量摊销，或缩短哪一段延迟。

### 15.5 把实现偶然细节写成永久语义

必须区分：

- 用户 ABI 和 POSIX 语义；
- 内核子系统接口约定；
- 当前版本的具体实现；
- 配置选项下才存在的路径；
- 便于优化但不保证稳定的字段布局。

## 16. 最终评价标准

一篇合格的内核机制文档，读者读完后应能够：

1. 从现实问题推导出为什么需要该机制；
2. 说出 Linux 方案相对简单方案的收益和代价；
3. 沿一个常见案例描述主要对象和状态变化；
4. 在源码中找到关键入口，并理解关键分支存在的原因；
5. 分析至少一个并发竞态或失败回滚过程；
6. 使用实际工具验证文章中的核心结论；
7. 面对新版本实现变化时，仍能依靠不变量重新理解代码。

写作时始终遵循下面这条主线：

```text
提出问题
→ 推导设计
→ 跟踪过程
→ 用代码证明
→ 分析并发与失败
→ 评价收益和代价
→ 通过实验验证
```

如果一段内容无法放进这条主线，应考虑把它移到附录、关键函数速查表，或者直接删除。

## 17. 新会话使用本规范的强制流程

本规范不仅描述文章风格，也定义新会话接到写作任务后的执行流程。新会话不得在只浏览目录或
部分章节后直接开始写作，必须完整阅读本文档。

### 17.1 启动阶段

收到“编写某个 Linux 内核机制文档”的任务后，依次执行：

1. 完整读取本规范；
2. 确认当前仓库、commit、内核版本和工作区状态；
3. 查找仓库中的 `AGENTS.md` 或其他局部规则；
4. 阅读与主题相邻的现有文档，避免内容冲突和重复；
5. 定位当前源码中的入口、核心对象、快速路径、慢速路径和释放路径；
6. 确定一个常见且可验证的贯穿案例；
7. 在进入函数细节前画出宏观地图；
8. 完成全文后核对函数、字段、配置条件和 Markdown 格式。

如果当前实现与常见旧版资料不同，以当前仓库源码为准，并在文档开头标明版本。

### 17.2 写作前必须明确的内容

开始正文前，作者必须能够回答：

```text
主题的历史和技术背景是什么？
用户或其他内核子系统遇到了什么具体问题？
最简单的方案是什么，它为什么不够？
Linux 的总体方案分为哪些层？
主要优点和工程代价是什么？
哪一个常见案例能够贯穿所有关键阶段？
案例会经过哪些子系统、对象和发布边界？
哪些结论可以通过当前源码和实验直接验证？
```

如果这些问题尚未回答，不应直接开始罗列结构体或函数。

### 17.3 强制执行顺序

新会话应按下列顺序工作：

```text
完整阅读规范
→ 检查当前源码和版本
→ 确定贯穿案例
→ 确定背景、问题和核心矛盾
→ 比较简单方案与 Linux 方案
→ 绘制宏观地图
→ 跟踪案例的真实调用过程
→ 提取能够证明结论的最小源码片段
→ 分析快速路径、慢速路径和失败回滚
→ 分析锁、引用、RCU、内存序与最终回收
→ 设计可执行验证实验
→ 核对源码符号、版本差异和格式
```

不得以“先生成完整草稿，之后再补背景和代码”为默认流程。背景、地图和案例决定文章结构，
应在深入细节之前完成。

### 17.4 可直接交给新会话的任务模板

```text

./doc/linux-kernel-internals-writing-guide.md

要求：

1. 基于当前仓库源码和当前内核版本，不使用未经核对的旧版资料。
2. 文档必须包含：
   - 历史和技术背景
   - 需要解决的具体问题

   - Linux 总体技术方案
   - 方案优点、代价、适用边界和替代方案
   - 子系统、对象关系、数据流三层宏观地图
   - 一个常见案例，并贯穿全文
3. 按案例的真实执行过程深入源码。
4. 关键结论必须用当前源码片段、状态变化或锁协议论证。
5. 同时讲快速路径、慢速路径、失败回滚和最终回收。

   - 竞态双方
```

## 18. 质量复现与交付验收

### 18.1 规范是必要条件，不是质量保证本身

仅仅声明“遵循本规范”不能保证质量。最终结果还取决于：

- 是否完整阅读规范；
- 是否真正检查当前源码；
- 是否选择了足以贯穿全文的案例；
- 是否用代码证明关键结论；
- 是否深入到并发、异常和生命周期；
- 是否执行交付前的符号与格式检查。

因此验收应依据文档内容，而不是作者是否声称使用了本规范。

### 18.2 推荐参考成品

新会话除阅读本规范外，可以使用以下文档校准深度和表达方式：

```text
写作结构与进程生命周期：
./doc/08 linux-process-management-internals.md

端到端异步流水线与分层对象：
./doc/12 linux-block-io-internals.md
```

参考成品的目的不是复制章节，而是校准：

- 前部是否明确给出背景、问题、优劣和宏观地图；
- 案例是否真正贯穿全文；
- 代码是否参与论证；
- 是否覆盖发布边界、失败路径和最终释放；
- 内容深度是否超过函数与结构体简介。

若参考文档中的函数与当前源码不一致，仍以当前源码为准。

### 18.3 交付前硬性门槛

以下任一项不满足，文档不应被视为完成：

- [ ] 开头明确给出历史/技术背景；
- [ ] 单独说明需要解决的问题和核心矛盾；
- [ ] 比较简单方案与 Linux 方案；
- [ ] 集中说明总体方案的优点、代价和适用边界；
- [ ] 在源码细节前给出子系统、对象关系和数据流宏观地图；
- [ ] 至少有一个常见案例贯穿主要章节；
- [ ] 至少三个关键结论由当前源码片段直接证明；
- [ ] 展示关键对象或字段的状态变化；
- [ ] 同时分析快速路径和至少一个慢速/退化路径；
- [ ] 至少分析一个具体并发竞态及其同步协议；
- [ ] 说明失败回滚或最终资源回收过程；
- [ ] 明确方案收益与对应代价，而非只写“提高性能”；
- [ ] 提供可执行或可观测的验证实验；
- [ ] 所有关键函数和字段已在当前仓库中核对；
- [ ] 已执行 Markdown/diff 格式检查。

### 18.4 禁止降级为平铺陈述

出现以下特征，说明文章虽然内容很多，但没有达到本规范要求：

```text
开篇直接列出十几个结构体；
每节都是“定义、字段、函数”三段式；
调用链只有箭头，没有状态和所有权变化；
所有优点都被概括成“提升性能”；
并发部分只写“通过加锁保证安全”；
案例只在开头或结尾出现一次；
调试章节只罗列命令，不说明预期证据；
大量引用旧版函数名，却没有在当前仓库核对。
```

发现这些问题时，应回到贯穿案例重新组织全文，而不是继续增加结构体和函数数量。

### 18.5 完成后的自我复述测试

作者应尝试不看正文，用几分钟回答：

1. 该机制为什么产生？
2. 它解决了哪些具体问题？
3. Linux 为什么没有选择最简单方案？
4. 宏观地图中有哪些层，数据和控制如何流动？
5. 贯穿案例从入口到完成经历哪些状态变化？
6. 最关键的源码证据是什么？
7. 哪个并发竞态最能体现实现复杂度？
8. 方案在哪些场景会退化或付出明显代价？
9. 如何通过实验观察这些结论？

如果无法形成一条连贯回答，说明文章仍然是知识点集合，需要继续重构。
